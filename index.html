1. Project overview

The Task Manager API is a backend application that exposes HTTP endpoints so a client—such as Postman, a browser-based frontend, or a mobile app—can create and manage tasks. The repository README lists task creation, listing, lookup by ID, updating, deleting, validation, exception handling, and unit testing.

PurposeManage task records through HTTP requests.
PersistenceStore application data in a relational database.
ReliabilityValidate input and test service behavior.
Portfolio valueDemonstrates API, database, testing and deployment concepts.
Project-specific note: the repository README confirms the core stack and task CRUD endpoints. Authentication/JWT, roles, Docker and PostgreSQL deployment have also been part of the project's development. Verify the current branch and configuration before describing any feature as live or production-deployed.

Typical user story

  1. A client sends a request to create a task.
  2. The API checks the request and applies business rules.
  3. The application saves the task through the persistence layer.
  4. The API returns an HTTP status and a response body.
  5. The client can later read, update or delete that task.

3. Layered architecture

A common Spring Boot structure separates HTTP handling, business rules, and database access. Treat this as the conceptual model; use the actual package and class names from your repository when presenting your implementation.

Client / Postman→Controller→Service→Repository→Database

Responsibilities

  • Controller: accepts HTTP requests, reads path/query/body data, and returns HTTP responses. Avoid putting substantial business rules here.
  • Service: implements application rules, coordinates operations, and is a natural unit-testing target.
  • Repository: provides data-access operations, commonly through Spring Data interfaces.
  • Entity: represents persisted data and its table mapping.
  • DTO (if used): defines the data accepted from or returned to API clients. DTOs help avoid exposing persistence details directly.
  • Exception handler (if used): converts exceptions into consistent HTTP error responses.
Why separate layers? It improves readability, testability, reuse and change isolation. A controller can change its HTTP mapping without requiring every database detail to be rewritten.

4. REST API and HTTP basics

REST-style APIs expose resources through URLs and use HTTP methods to express the requested operation. This project's README lists the following task routes:

MethodEndpointPurposeCommon success status
POST/tasksCreate a task201 Created (or 200 OK if implemented that way)
GET/tasksRetrieve tasks200 OK
GET/tasks/{id}Retrieve one task200 OK; 404 if absent
PUT/tasks/{id}Update a task200 OK or 204 No Content
DELETE/tasks/{id}Delete a task204 No Content or another documented success response

These are the endpoint paths from the README. The exact status codes, request fields, response JSON and authentication requirements must be checked in the current controller and security configuration.

HTTP status codes worth knowing

  • 200 OK — request succeeded and a response is returned.
  • 201 Created — a resource was created.
  • 204 No Content — request succeeded with no response body.
  • 400 Bad Request — request data is invalid or malformed.
  • 401 Unauthorized — authentication is missing or invalid.
  • 403 Forbidden — caller is authenticated but lacks permission.
  • 404 Not Found — requested resource does not exist.
  • 500 Internal Server Error — unexpected server-side failure.

Example request

POST /tasks
Content-Type: application/json

{
  "title": "Revise Spring Boot",
  "description": "Practise controllers and services"
}

Illustrative JSON only. Adjust field names and required properties to match the DTO/entity in the repository.

5. What happens when an API request arrives?

  1. The client sends an HTTP request to the application URL.
  2. If security filters are configured, they check whether the route requires authentication and whether the supplied credentials/token are acceptable.
  3. Spring MVC finds a matching controller mapping.
  4. Spring converts JSON into a Java request object when the method expects a body.
  5. Validation runs if the endpoint uses validation annotations and the appropriate validation trigger.
  6. The controller calls the service layer.
  7. The service applies business rules and calls the repository.
  8. JPA/Hibernate executes database operations inside the configured transaction boundary.
  9. The result travels back through the service and controller.
  10. Spring serializes the response object as JSON and sends an HTTP status.
When debugging, check one layer at a time: URL and HTTP method → security → controller mapping → request JSON/validation → service logic → repository/database → response serialization.

6. Spring concepts used in a backend project

Dependency Injection (DI)

Dependency Injection means a class receives the objects it depends on instead of constructing every dependency itself. Spring's IoC container creates and wires managed objects called beans.

@Service
public class TaskService {
    private final TaskRepository taskRepository;

    public TaskService(TaskRepository taskRepository) {
        this.taskRepository = taskRepository;
    }
}

This is a generic constructor-injection example. Use the names and patterns present in your actual project.

Important annotations

AnnotationMeaning
@SpringBootApplicationCommon application entry-point annotation; combines configuration, auto-configuration and component scanning.
@RestControllerMarks a controller whose return values are typically written to the response body.
@RequestMappingDefines a base or specific request mapping.
@GetMapping, @PostMappingMap HTTP GET and POST requests.
@PathVariableReads a value from the URL path, such as the task ID.
@RequestBodyDeserializes the request body into a Java object.
@ServiceMarks a service component for Spring's component scanning.
@RepositoryMarks a persistence component; Spring Data repository interfaces often provide the implementation.
@EntityMarks a JPA entity.
@IdMarks the primary-key field.
@ManyToOneModels many rows/entities associated with one related entity; this project setup has tasks associated with users.

@ValidTriggers bean validation for a supported method parameter.

Why constructor injection?

  • Dependencies are explicit and can be declared final.
  • Tests can supply mocks without starting the full Spring context.
  • Required dependencies are available when the object is constructed.

7. Database, entities and JPA

A relational database stores information in tables. Rows represent individual records and columns represent fields. Primary keys uniquely identify rows; foreign keys connect related tables.

Entity relationship in this project

The project setup includes users and tasks. A task has a many-to-one relationship to a user through a user_id foreign key; the task's user reference has been configured as non-nullable in the current project design.

USER (one)  ─────────  (many) TASK
  user id  <──────────  task.user_id

In Java, @ManyToOne represents the object relationship, while the database foreign key enforces referential integrity. A foreign key prevents a task from referring to a user row that does not exist.

JPA versus Hibernate

  • JPA is the Java persistence specification: it defines standard APIs and annotations.
  • Hibernate is a common implementation of JPA.
  • Spring Data JPA adds repository abstractions to reduce persistence boilerplate.

Schema validation

With Hibernate schema mode set to validate, Hibernate checks that mapped entities are compatible with the database schema at startup rather than automatically creating or altering the schema. Schema changes should be managed deliberately, for example with Flyway migrations.

8. Flyway database migrations

Flyway records which versioned SQL migration scripts have been applied. This makes schema changes traceable and helps developers apply them in a consistent order across environments.

MigrationPurpose in this project setup
V1Create the users table.
V2Create the tasks table.
V3Add indexes.

How it works

  1. Place a versioned SQL file in the configured Flyway migration location.
  2. Use a unique, ordered name such as V4__add_task_due_date.sql.
  3. On startup, Flyway checks its schema-history table.
  4. Flyway applies migrations that have not yet run and records their status/checksum.
  5. Hibernate validates entity mappings against the resulting schema if validation is enabled.
Important: after a migration has been applied to a shared or deployed database, do not casually edit the old migration. Create a new migration for the next schema change. Never paste database passwords or JWT secrets into public source code.

Useful checks

-- Example only; adapt schema/table names to your database
SELECT version, description, success
FROM flyway_schema_history
ORDER BY installed_rank;

Oracle column names and identifier casing can require quoting depending on how objects were created. If a query fails with an invalid identifier, inspect the table definition and column names rather than guessing.

9. Validation and exception handling

Validation rejects invalid input before it can cause inconsistent application data. Common Bean Validation annotations include:

  • @NotBlank — a string must contain a non-whitespace character.
  • @NotNull — a value must not be null.
  • @Size — a value's size must be within a specified range.
  • @Positive — a numeric value must be greater than zero.

These are examples; use only constraints appropriate for your actual request fields.

Exception handling

When a requested task ID does not exist, the service can signal a not-found condition and the API can return a meaningful 404. Invalid request data usually maps to 400. A centralized handler such as one using @RestControllerAdvice can keep error response formats consistent, if implemented in the project.

Good error response principles

  • Give the client a useful message and correct status code.
  • Do not expose stack traces, secrets, SQL credentials or internal implementation details.
  • Log diagnostic details on the server side.
  • Test both success and failure cases.

10. Authentication, JWT and authorization

The project has included Spring Security and JWT-based authentication in its development. Verify the current code/configuration before assuming every environment has the same security setup.

Authentication versus authorization

  • Authentication: who is making the request?
  • Authorization: is that identity allowed to perform this operation?

Typical JWT request flow

  1. A client submits login credentials to the authentication endpoint.
  2. The server verifies the credentials.
  3. The server issues a signed token with configured claims and expiry.
  4. The client sends the token in the Authorization: Bearer ... header on protected requests.
  5. A security filter validates the token and establishes the authenticated principal.
  6. Authorization rules decide whether that principal can access the endpoint.

Project details to remember

  • The JWT secret property used in the project is named app.jwt.secret.
  • The remembered default token expiration is 86400000 milliseconds (24 hours), unless overridden by configuration.
  • The user model uses a role field, with role values such as USER and ADMIN.
  • Method-level authorization has been configured for some operations; remembered examples include ADMIN-only task creation and USER/ADMIN access to listing tasks.
  • Password fields should never be returned in API responses. The project has used @JsonIgnore for the password field; dedicated response DTOs are another option.
A JWT secret must be long, random and supplied through environment variables or a secret manager in deployed environments. Do not commit real credentials. Do not claim that JWT encrypts the payload: a signed JWT is generally integrity-protected, not secret by default.

11. Unit testing with JUnit 5 and Mockito

Tests help detect regressions when the application changes. JUnit 5 provides test structure and assertions; Mockito lets a test replace collaborators with mocks.

Typical service unit-test pattern

  1. Create the service under test.
  2. Mock the repository or other external dependency.
  3. Arrange the mock's expected behavior.
  4. Call the service method.
  5. Assert the result or exception.
  6. Verify important interactions when useful.
// Generic illustration, not a copy of a project test
@ExtendWith(MockitoExtension.class)
class TaskServiceTest {
    @Mock
    TaskRepository taskRepository;

    @InjectMocks
    TaskService taskService;

    @Test
    void exampleTest() {
        // Arrange: configure a mock
        // Act: call the service
        // Assert: check the expected result
    }
}

The remembered project test run had 8 Mockito service tests passing at that point. Re-run tests to confirm the current state before reporting this number in a resume or interview.

Useful test cases

  • Create a task with valid data.
  • Retrieve all tasks, including the empty-list case.
  • Retrieve a task that exists.
  • Request an ID that does not exist.
  • Update a task successfully and handle a missing task.
  • Delete an existing task and handle a missing task.
  • Reject invalid input.
  • Check authorization for protected endpoints.

Run tests

# Windows PowerShell, from the project root
.\mvnw.cmd test

# If the project does not include the Maven Wrapper
mvn test

12. Docker and deployment basics

Docker packages an application and its runtime into an image. A container is a running instance of that image. Docker can make application startup more repeatable, but it does not automatically provide a database or make the application production-ready.

Terms

  • Dockerfile: instructions to build an image.
  • Image: packaged filesystem and runtime layers.
  • Container: a running instance of an image.
  • Port mapping: connects a host port to a container port.
  • Environment variable: passes configuration without hardcoding it in the image.
  • Docker Compose: defines and runs multiple related services.

The project setup has used an Eclipse Temurin Java 21 JRE base image. A previous local Compose setup mapped host port 8084 to application port 8083 and used host.docker.internal to reach an Oracle database running on the host. These are environment-specific settings, not universal production defaults.

Deployment checklist

  • Build and test the application.
  • Supply the database URL, username and password via environment variables/secrets.
  • Supply a secure JWT secret through secret configuration.
  • Confirm the app listens on the port expected by the hosting platform.
  • Check database network access and run migrations safely.
  • Read deployment logs and test a health endpoint or a known API route.
  • Never assume a local Oracle connection string will work on a remote host.

13. Configuration and common troubleshooting

Spring Boot configuration commonly lives in src/main/resources/application.properties or application.yml. Keep environment-specific values outside source control where possible.

Typical configuration categories

  • Server port
  • Datasource URL and credentials
  • JPA/Hibernate behavior
  • Flyway migration settings
  • JWT secret and expiry
  • Logging levels

Common problems

SymptomWhat to check
Application cannot connect to databaseDatabase service status, hostname, port, service name, credentials, network and JDBC URL.
Flyway migration failsSQL syntax, migration order, schema permissions and whether a prior migration partially changed the schema.
Hibernate validation failsEntity/table/column names, data types, nullability, foreign keys and applied migrations.
401 responseWhether a token is required, token format, expiry, signing secret and authentication filter configuration.
403 responseAuthenticated role/authorities and endpoint/method authorization rules.
404 for an endpointRequest path, HTTP method, controller mapping and any base path.
Port already in useFind the process using the port or configure a different application port.
Works locally but fails in DockerContainer port, host port mapping, environment variables, DNS/network and database reachability.

Safe workflow for a schema change

  1. Update or add the Flyway migration.
  2. Update the corresponding entity mapping.
  3. Run against a development database first.
  4. Run automated tests and start the app with schema validation enabled.
  5. Inspect the migration history and verify the affected endpoint.
  6. Commit the change with a clear message.

14. Interview questions and sample answers

1. Explain your project in brief.

“I developed a Task Manager REST API using Java and Spring Boot. It exposes endpoints to create, retrieve, update and delete tasks. The project uses Spring Data JPA for persistence, Oracle with Flyway for database schema changes, and JUnit 5 with Mockito for testing. I also worked on validation, exception handling and security/deployment features as part of the project.”

Only mention security and deployment features that you can demonstrate in the current code.

2. Why did you use Spring Boot?

Spring Boot provides auto-configuration and convenient application setup, reducing boilerplate compared with configuring every component manually.

3. What is a REST API?

It is an HTTP-based interface that exposes resources through endpoints and uses methods such as GET, POST, PUT and DELETE to communicate operations.

4. What is dependency injection?

It is a technique in which an object receives its dependencies from an external container or caller rather than constructing them itself. Spring's container manages beans and their dependencies.

5. Why use service and repository layers?

The service layer holds application/business rules, while the repository layer handles persistence. Separating responsibilities improves maintainability and testing.

6. What is JPA? What is Hibernate?

JPA defines the standard persistence API and mapping model; Hibernate is a widely used implementation of that specification.

7. Why use Flyway?

Flyway versions database changes as ordered migrations and records which scripts have run, making schema evolution more repeatable across environments.

8. What does schema validation do?

Hibernate's validation mode checks entity mappings against the existing database schema at startup; it does not replace a deliberate migration strategy.

9. What is the difference between PUT and POST?

POST commonly creates a subordinate resource or submits an operation. PUT commonly replaces or updates the resource identified by the target URL and is designed to be idempotent.

10. What is the difference between 401 and 403?

401 means valid authentication has not been established. 403 means the request is understood but the authenticated caller is not allowed to perform it.

11. What is JWT?

JWT is a compact token format that can carry claims. In a typical signed-token flow, the server verifies the signature and expiry before trusting the claims.

12. Authentication versus authorization?

Authentication verifies identity; authorization checks permissions for an operation or resource.

13. Why validate request data?

Validation rejects malformed or out-of-range input early, protects business rules and gives clients clear feedback.

14. How do you handle a task ID that does not exist?

The service should identify the missing resource and the API should return a meaningful not-found response, typically HTTP 404, using the project's chosen exception-handling approach.

15. What is unit testing?

Unit testing checks a small unit of code in isolation. For a service, I can mock the repository and test success and failure paths without requiring a real database.

16. Why Mockito?

Mockito creates mocks and stubs so tests can control dependency behavior and verify interactions where necessary.

17. Why use Docker?

Docker packages the app and runtime into a portable image and helps run it consistently across environments, with external configuration supplied separately.

18. How would you improve this project?

Depending on what is already implemented, I would consider API documentation, stronger integration tests, pagination and filtering, structured logs, health checks, secure secret management, CI automation, and a deployed demo. I would first inspect existing features to avoid duplicating work.

30-second project pitch

“My project is a Task Manager REST API built with Java and Spring Boot. It provides CRUD endpoints for tasks and uses Spring Data JPA to persist data in a relational database. I used Flyway to manage schema changes and JUnit 5 with Mockito to test service logic. Building it helped me understand REST API design, layered architecture, database integration, error handling and automated testing.”
